# Architecture Decisions — Release 1 + Release 2

## Framework & Topology

### FastAPI framework choice

- What it is. FastAPI is an async-capable Python web framework that produces an OpenAPI schema from type-annotated route declarations and validates requests/responses with Pydantic models.
- Alternatives. (1) Flask — lighter but no built-in schema or validation. (2) Django — heavier, opinionated ORM and auth that would fight the modular boundary. (3) Starlette-only — would require hand-building schema and validation.
- Why this one. The product needs typed request/response contracts, dependency-injected auth, and Prometheus instrumentation. FastAPI gives all three without a separate API-contract step. Pydantic validation is the same library used across the domain models (`providers`, `evaluation`, `query_runs`), so the trust boundary is uniform — a malformed provider response is rejected at the same seam the API rejects a malformed browser payload.
- When you would choose differently. If the product later requires a synchronous-only worker pool (no `asyncio` event loop), FastAPI's async flavour becomes dead weight. A WSGI framework would be simpler. If the API surface grows to hundreds of endpoints, a schema-first approach (OpenAPI → codegen) would reduce drift.
- How it serves the purpose. FastAPI's `APIRouter` lets each module (`query_runs`, `model_slots`, `readiness`) own its route tree. The app shell in `main.py` mounts them; no router touches another's state. The OpenAPI schema doubles as the contract test input (`docs/22-api-contract.md`), and gating the interactive docs behind `api_docs_enabled` keeps the CSP clean in production.

### Single-worker deployment (why single, not multi-worker or async workers)

- What it is. The Fly.io `fly.toml` configures one FastAPI service process with one Uvicorn worker. The in-memory stores (`query_run_repository`, `cost_event_recorder`, `feedback_store` singletons) are module-level process-global objects; the run pipeline fans out via `ThreadPoolExecutor` pools inside that one process.
- Alternatives. (1) Multi-worker Uvicorn (e.g., `--workers 4`) — requires each worker to own its own store instances or share state through an external broker. (2) Celery / Dramatiq async workers — extracts the orchestration pipeline into a separate process that consumes jobs from a queue. (3) ASGI-native `anyio` task groups inside FastAPI — keeps one process but replaces threads with structured concurrency.
- Why this one. The MVP's in-memory stores (`InMemoryQueryRunRepository`, `InMemoryCostEventRecorder`, the feedback/run-history SQLite singletons) are process-global singletons with a single `RLock`. Multi-worker deployments would duplicate or race on those locks without an external coordination layer. Adding a broker (Redis, Postgres LISTEN/NOTIFY) is the correct next step, but it is work the MVP does not need to pay for before correctness, safety, and cost discipline are proven.
- When you would choose differently. If the deploy moves to two or more Fly machines (multi-instance), the SQLite single-writer ceiling (ADR-0002) becomes a data-integrity risk and a broker (e.g., `fly-postgres`) becomes necessary. If the run rate grows to where the `_MAX_CONCURRENT_RUNS` semaphore is routinely saturated, an external job queue lets the API scale horizontally while the worker pool scales independently.
- How it serves the purpose. Single-process keeps the lock discipline simple (one `RLock` per singleton, one SQLite connection per store) and makes the run-cap semaphore (`_run_semaphore`) the only admission control. The `ThreadPoolExecutor` pools (`_initial_answer_pool`, `_synthesis_pool`) give parallelism inside the run without touching the store's single-writer lock. This is a ceiling we chose after measuring it, not a default we inherited.

### Modular monolith vs microservices (ADR-0001)

- What it is. A modular monolith is a single deployable service whose internal modules (`auth`, `orchestration`, `providers`, `safety`, `persistence`, `observability`) communicate through in-process function calls and shared value objects, with explicit ownership boundaries enforced by code review and import structure rather than network boundaries.
- Alternatives. (1) Four independent chatbot integrations in the browser: provider credentials, cost controls, and observability would all live client-side. (2) Fully distributed microservices for the MVP: each module becomes a separately deployed service with its own schema, queue, and deployment lifecycle. (3) Anonymous execution: no auth, no cost guardrail, no session scoping.
- Why this one. The MVP's risk surface (provider spend, secret exposure, high-stakes output, prompt injection) is controlled by keeping the orchestration logic, provider keys, and cost thresholds server-side. A monolith makes that boundary obvious. The internal seams are already expressed as separate modules with documented ownership (`docs/20-architecture.md` Components table); extraction into workers/services later is a refactor, not a rewrite. ADR-0001 status: Draft — recorded but not yet validated against the threat model.
- When you would choose differently. If provider volume or latency requires horizontal scaling of the orchestration layer independently of the API surface, or if different team boundaries need independent deploy cadences, microservice extraction becomes the right cost. If the product moves to durable account login with shared state across clients, a service boundary around `auth` and `persistence` becomes useful earlier.
- How it serves the purpose. One service means one deploy, one log stream, one `_run_semaphore` admission control, and one SQLite file per store. The failure domain is the whole process, but the failure mode is well-understood (the `try/except` in `_execute_query_run_safely` always reaches a terminal state). The trade-off accepted is that scaling is process-bound until extraction is proven necessary by measurement.

## Data

### SQLite file database vs external RDBMS vs in-memory (ADR-0002)

- What it is. Two durable stores (`feedback_store`, `run_history_store`) use a single `sqlite3.Connection` opened with `check_same_thread=False` and `isolation_level=None` (autocommit), guarded by one `threading.RLock`, in the default `journal_mode=DELETE`. The in-memory query-run repository is a separate ephemeral store with TTL-based eviction.
- Alternatives. (1) External RDBMS (Postgres via `fly-postgres`) — eliminates the single-writer ceiling and supports multi-instance, but adds a managed dependency, connection pooling, and a new failure domain. (2) WAL journal mode — measured 4–5× faster on synthetic benchmarks, but adds sidecar `-wal`/`-shm` files on the Fly volume and an unvalidated durability profile under Fly machine restart. (3) In-memory only — simplest, but loses every durable record on deploy or process restart.
- Why this one. The measured single-writer ceiling is ~4 500 writes/s per store. The real demand is well under 1 write/s per concurrent run (roughly three orders of magnitude of headroom). The correctness test (`tests/test_store_concurrency.py`) proves no lost writes, no `database is locked`, and monotonic AUTOINCREMENT ids at 32 threads / 256 writes. ADR-0002 status: Accepted — 2026-07-19.
- When you would choose differently. When a measurement shows the ceiling is being approached, or when the deployment moves to multi-instance (two Fly machines sharing a volume would break this design; that path needs Postgres, not a journal-mode change). A bulk backfill or evaluation replay over history is the most likely demand-growth scenario.
- How it serves the purpose. The `WeakSet` + `atexit` + `__del__` lifecycle fixes the unclosed-database leak without changing the write path. The `configure()` / `close()` idempotency lets tests swap stores without tearing down the singleton. The separate `run_history_store` (one row per terminal run, `INSERT … ON CONFLICT DO UPDATE`) and `feedback_store` (append-only event trail) keep the concerns clean: the audit job reads events; the evaluation engine reads run metrics.

### In-memory query-run repository (ephemeral, session-scoped)

- What it is. `InMemoryQueryRunRepository` holds every active and recently-terminal run in a `dict[UUID, QueryRun]` guarded by one `RLock`. Terminal runs are evicted after `QUERY_RUN_TERMINAL_TTL` (1 hour); active runs that never reach a terminal state are evicted after `QUERY_RUN_ACTIVE_TTL` (30 minutes). The durable `run_history_store` persists the terminal record separately.
- Alternatives. (1) SQLite-backed run repository — would give durability across deploys for in-flight runs, but adds contention on the same single-writer store the event trail already uses. (2) Redis — fast and multi-instance-safe, but introduces a new external dependency for a demo product. (3) Process-global list without TTL — unbounded growth.
- Why this one. The MVP only needs run state to survive the polling window (the browser reads results via `GET /v1/query-runs/{id}`). A 1-hour terminal TTL is generous. The separate `run_history_store` write at the terminal transition is the durable record; the in-memory store is the live view.
- When you would choose differently. If the product adds long-lived saved-research history (out of scope per `docs/21-domain-model.md` Assumptions), the in-memory repository becomes the wrong tool. If deploys become frequent enough that a 30-minute active TTL causes visible result loss, a disk-backed repository is warranted.
- How it serves the purpose. TTL-based eviction is the GC strategy; the 60-second wall-clock check in `_purge_expired_locked` (replacing the old counter-based check) fires promptly under burst without scanning on every op. The active-query limit (`get_active_for_account`) and the state-machine transition guard (`ALLOWED_TRANSITIONS`) both live here, so correctness is local to one module.

## Pipeline

### Four model slot system (why four, not one or N)

- What it is. Every accepted query run fans out to exactly four `ModelSlot` values, each carrying a `model_id`, a `search` flag, and a display label. The domain model requires four slots for execution; the `validate_model_slots_with_search` helper enforces exactly four on the request path.
- Alternatives. (1) One model — simplest, but collapses the product's core value proposition (cross-model comparison) into a single chatbot. (2) N configurable slots — maximally flexible, but the cost-estimation arithmetic, the debate prompt template, and the synthesis prompt all hard-code a four-answer assumption; generalising to N would require reworking every downstream consumer.
- Why this one. Four is the panel size the domain model was designed around. The debate prompt summarises four answers in 200-character excerpts; the synthesis prompt reads "Four model answers"; the `AgreementSummary` is "aligned of total" where total is the slot count. Four gives enough diversity for meaningful disagreement while keeping the prompt construction bounded. The default four slots cover four vendor families (OpenAI, Anthropic, Google, NVIDIA), which gives geographic and architectural diversity without the user having to think about it.
- When you would choose differently. If the product later wants to support an arbitrary number of models per run (e.g., a user-curated panel), every downstream consumer — the debate summariser, the synthesis prompt, the cost estimator, the agreement classifier — must be reworked to handle a variable count. The `ModelSlot` dataclass and the cost arithmetic are the two places that would need the most surgery.
- How it serves the purpose. Four slots make the cost model tractable (four fixed initial calls, two fixed debate rounds, one fixed synthesis) and make the agreement signal interpretable (4-of-4 vs 3-of-4 vs 2-of-4). The `search` flag is per-slot, so the user can opt individual models into or out of web search, which is the only per-slot variation the current model supports.

### Debate-then-synthesize pipeline (why this order, not other patterns)

- What it is. The pipeline runs four initial model answers, then two critique/debate rounds over those answers, then one synthesis step that produces consensus, disagreement, source support, uncertainty, and recommendation sections. The debate rounds are optional (the pipeline degrades to synthesis only when the debate budget is exhausted), but they always precede synthesis.
- Alternatives. (1) Direct synthesis without debate — simpler and cheaper, but loses the explicit disagreement and weak-support signals the domain model requires. (2) Interleaved debate (debate after each answer) — more realistic but multiplies the number of LLM calls (up to 8 debate rounds) and makes the cost model and timeout budget much harder. (3) Synthesis first, then debate on the synthesis — inverts the intended signal: the debate would be critiquing a summary rather than the raw answers, losing the traceability to individual model positions.
- Why this one. The debate rounds exist to surface disagreement, weak source support, and missing reasoning before the synthesis condenses the panel's output. Running debate first means the synthesis prompt carries the critique inline and the model can preserve or resolve disagreement deliberately. The two rounds are fixed: round 1 identifies the strongest residual concerns, round 2 refines them. The `DEBATE_HARD_TIMEOUT_MS` (180 s) and the round-2 skip budget mean the debate cannot stall the run.
- When you would choose differently. If the product moves to a streaming or real-time comparison UI, interleaving debate with answers might feel more natural. If the cost model shifts to per-token billing without a run-level cap, reducing the debate to one round or skipping it entirely becomes the cost optimisation.
- How it serves the purpose. The debate-then-synthesize order is what gives the product its "cross-validation" framing: the user sees the models' initial answers, then the critique of those answers, then the curated synthesis. Removing the debate step would reduce the product to a multi-model chatbot with extra steps, and the domain model's requirement that the synthesis preserve material disagreement would be unenforceable.

### Cost confirmation gate (why confirmation required, not estimation only)

- What it is. The cost gate is a three-band system: `ALLOW` for estimated worst-case cost ≤ `soft_threshold_usd` (USD 0.15), `REQUIRE_CONFIRMATION` for costs in (USD 0.15, USD 0.25], and `BLOCK` for costs above `hard_limit_usd` (USD 0.25). Confirmation tokens are bound to the `account_id`, `query_run_id`, `estimated_cost_usd`, and an expiry timestamp via an HMAC; replay across accounts, after expiry, or with a mismatched cost is rejected. A cumulative-spend guard (in-memory event ring) and a per-account daily cap (durable SQLite) provide defense-in-depth beyond the per-call gate.
- Alternatives. (1) Estimation only with a warning — relies on the user reading and heeding a number; no enforcement. (2) Hard block at a single threshold — simpler, but prevents the user from knowingly accepting a higher-cost query. (3) Per-model budget allocation — lets the user distribute a budget across slots, but multiplies the state machine complexity.
- Why this one. The product's cost risk is asymmetric: a runaway query can spend real money on the operator's  key. A confirmation gate forces the user to acknowledge the cost before the run starts, and the three-band design gives the operator a soft nudge (confirmation) and a hard stop (block) without preventing legitimate higher-cost queries. The token-binding design means the confirmation is non-repudiable and non-transferable. The cumulative and daily caps close the "trickle out many small queries" attack that the per-call thresholds miss.
- When you would choose differently. If the product moves to a BYO-key-only model where the user pays their own provider bill, the operator's cost guardrails become advisory rather than mandatory, and the gate would shift to a warning + rate-limit design. If the product adds subscription tiers, each tier would carry its own threshold values.
- How it serves the purpose. The gate is the only place the system says "no" to a valid query, so it must be honest. The `max_cost_usd` (fail-safe upper bound) is always ≥ `estimated_cost_usd` (realistic point estimate), and the guardrail keys off the bound, so the gate can only over-protect — a run can never bill past a limit it was waved through under. The estimate-accuracy log (`_log_estimate_accuracy`) exists because the gate is only as good as the estimate; a systematically low estimate would silently weaken the rail.

### Layer B evaluation (judge layer) — OFF by default

- What it is. Layer B is an optional LLM-as-judge (`EvalJudgeService`) that reuses `providers.call_with_prompt`, is key-gated on `QUORUM_EVAL_JUDGE_API_KEY`, and is OFF by default. When enabled, the judge receives a strict-JSON prompt containing the query text, model answers, sources, and synthesis sections inside delimited evidence blocks; a malformed or non-conforming response yields no verdict. The judge verdict is advisory metadata that never enters the `TrustScore` arithmetic. A deterministic `StubEvalJudge` (which deliberately does not verify support) is used in CI so judge-OFF and stub-ON are byte-identical.
- Alternatives. (1) Layer B always on — would make every run incur an extra paid LLM call and would break the hermetic-CI requirement (NFR-011). (2) Layer B as the primary score — would make the trust signal depend on a paid, non-deterministic model whose output can be adversarially influenced by provider prose (prompt injection via verdict, T-011). (3) Human-in-the-loop evaluation only — would require a review queue and would not produce per-run signals at read time.
- Why this one. The binding honesty rule (OC-2) is that citation-count coverage cannot verify that a citation supports its claim. Therefore `support_verified` is False unless a real Layer-B judge returned a verdict, and while it is False the numeric score is suppressed. Keeping Layer B OFF by default means every hermetic CI run and every default deployment serves `"unverified"` with zero latency, zero cost, and zero delta versus the deterministic path (NFR-012). When the operator configures both the API key and a pinned model ID, the real judge is memoised per run (first outcome wins; bounded LRU of 512) so N polls of one terminal run make at most one paid call.
- When you would choose differently. When the S4 golden set exists and the judge has been calibrated against it, the operator may choose to enable Layer B in production. Until then, enabling it would ship an uncalibrated advisory label that could inflate trust on an unfaithful answer (AB-007). The judge should never be the only signal; Layer A is the always-on floor.
- How it serves the purpose. Layer B is advisory metadata, never a control path. A compromised judge cannot raise the numeric score because the judge never enters the composite arithmetic. The strict-JSON output contract (Pydantic `EvalJudgeVerdict` with `strict=True, extra="forbid"`) means a judge that cannot follow "reply with JSON and nothing else" is a judge whose verdict the system has no reason to trust. The `_neutralize_delimiters` function stops provider prose from forging the end-of-evidence delimiter, and the system prompt explicitly labels the evidence block as untrusted data.

### Tavily provider strategy

- What it is. When 's `:online` web-search suffix fails or returns no usable source support, the `ProviderExecutionService` falls back to the Tavily search adapter (if `TAVILY_API_KEY` is set). If Tavily is also unavailable, the run falls back to `LOCAL_SIMULATION` with a user-safe provider notice. The fallback path is gated by the same operator-opt-in mechanism as live execution: a missing key or a hard call failure both fall back silently, with a `provider_notice` added to the response.
- Alternatives. (1) No fallback — a failed  search means no sources, which degrades citation coverage and the trust signal, but the run still completes. (2) Multiple fallback providers — more resilient, but each additional adapter multiplies the provider-key surface and the retry-state machine. (3) Browser-side search — rejected because it would expose the fallback key and break server-side observability.
- Why this one. The MVP needs source-backed answering (FR-006); if the primary path fails, the user gets a partial result with a degraded source set, not a 500. Tavily is the approved fallback because it is the one the product owner specified (OQ-008, now resolved). The fallback is visible: every source returned by Tavily carries `is_fallback=True`, and the UI surfaces a degraded banner when `live_count < 4` so simulated or fallback output is never presented as live.
- When you would choose differently. If Tavily's pricing, rate limits, or terms change, the operator would swap to another approved fallback (the adapter contract is the same `ProviderPath.FALLBACK_SEARCH` interface). If the product moves to a BYO-key-only model, the fallback key becomes a user responsibility and the operator no longer needs to carry it.
- How it serves the purpose. The fallback is transparent: the `ProviderPath` enum records the exact path taken (`LOCAL_SIMULATION`, `OPENROUTER_SEARCH`, `FALLBACK_SEARCH`), and the `provider_attempt_order` list on each `InitialModelAnswer` records every attempt. The cost estimator prices searching slots with a flat per-request web-search plugin fee (issue #18), so the estimate is honest whether the slot uses 's `:online` or falls back to Tavily.

## Auth

### Session-based auth vs durable account login

- What it is. The MVP uses an opaque browser session cookie plus CSRF token (`auth.py`) instead of durable account login. BYO  keys are stored server-side only and keyed to the current session. Query runs and results are held in ephemeral in-memory session-scoped storage for this slice.
- Alternatives. (1) Durable account login with email/password or OAuth — requires user-management infrastructure (password hashing, email verification, password reset, account deletion) that the MVP does not need. (2) API-key-only auth — simpler, but loses the browser-session semantics (CSRF, cookie expiry, session revocation). (3) Anonymous with rate-limit — rejected by FR-001 because it creates abuse and cost risk.
- Why this one. The MVP's auth requirement is "one authenticated query workflow" (FR-001). Session cookies give the product an identity boundary for cost tracking, result access, and BYO-key scoping without the overhead of durable accounts. The session is opaque to the server (a UUID), which means the product does not need to store or manage user credentials. The CSRF token is required on every mutating endpoint, which prevents cross-site request forgery against the cost gate and query creation paths.
- When you would choose differently. If the product adds saved research history, cross-device sync, or multi-user collaboration, durable accounts become necessary. If the product is embedded in a larger platform, the auth boundary moves to the platform's identity provider and the session cookie becomes a bearer token issued by the platform.
- How it serves the purpose. Session auth is the temporary security boundary for the MVP: it protects quota, result access, and BYO-key scope until durable accounts are introduced. The `require_session` dependency is the only gate on execution and result-read endpoints, and the `enforce_csrf` helper is called explicitly on every mutating route. Wrong-identity result access and BYO-key management are denied by the `get_for_account` ownership check on the repository.

## Evaluation

### Layer A design (deterministic, always-on, hermetic)

- What it is. Layer A is a pure function of a terminal run's in-memory value objects. It computes citation coverage, citation-marker grounding, agreement ratio, live ratio, completeness, false-consensus preservation, decision-support framing, high-stakes warning presence, uncertainty surfaced, refusal detection, and polar disagreement — all from the run's own data with zero I/O, zero network, and zero clock dependency. Its signals are the only input to the `TrustScore` composite arithmetic.
- Alternatives. (1) Always-on LLM judge — would make every run incur a paid call and would break hermetic CI. (2) Sampling-based evaluation — would leave most runs unevaluated, which defeats the purpose of a per-run trust signal. (3) Rule-based heuristic without the citation-marker census — cheaper, but would miss the grounding signal that separates the adversarial corpus pair (faithful vs fluent-unfaithful).
- Why this one. Layer A is the only evaluation path that ships in the MVP slice. It is deterministic (same run → byte-identical `RunEvaluation`), always on (no key, no network, no cost), and hermetic (zero I/O). The citation-marker census (`_scan_links`, `extract_citation_markers`) is the technically expensive part — it is a bracket-balanced single-pass scanner bounded per step — but it runs in milliseconds on real output. The `RefusalMAJORITYTHRESHOLD` (0.5) and `GROUNDING_FABRICATION_THRESHOLD` (0.5) are advisory constants that pin direction, not accuracy; the corpus (five hand-authored cases) is not large enough to calibrate magnitude.
- When you would choose differently. When the S4 golden set exists (measured real-run corpus), the weights and thresholds in `LAYER_A_WEIGHTS` and the band cuts (`BAND_LOW_CEILING`, `BAND_MODERATE_CEILING`) can be recalibrated. If the product later requires per-claim attribution (not just per-run signals), Layer A would need to be extended with a finer-grained census.
- How it serves the purpose. Layer A's honesty rule is that it can only establish what its signals can actually establish. Citation-count coverage is one signal; citation-marker grounding is a separate, harder signal that requires reading the prose. The `support_verified` flag is False unless a real Layer-B judge confirms support, and while it is False the numeric score is suppressed. This is the structural guarantee that a fabricated citation cannot silently inflate trust.
