# The map: where each kind of information lives

Read this before looking for anything. One kind of information has ONE home.
If you find the same kind in two places, the row below says which one is the
original; the other is a copy, a mirror, or history.

Why this exists: measured on 2026-09-30 at `7c74b4f`, a new agent following
links from `AGENTS.md` reached 35 of 538 tracked `.md` files in one hop and
270 within three; **268 were not reachable within three links**
(`python3 scripts/measure_doc_reachability.py`). Decisions, open work and
session records each had several homes. The product owner asked that a fresh
session be able to find the right file without guessing.

## One row per kind of information

| Kind of information | Its ONE home | Kept current by | Read it when |
|---|---|---|---|
| How to work in this repository (the rules) | `AGENTS.md` (`CLAUDE.md` includes it) | Hand-written; `tests/test_doc_gate_consistency.py` pins the numbers it states about the tree | Every session, first |
| What is open, what blocks it, what proves each row's state | `docs/65-open-work.md` (the board) | State derived from the tree by `scripts/check_open_work.py --check` inside `make validate`; GitHub issues are the mirror, not the original | Before choosing work |
| What the last session did and the traps it paid for | `docs/session-handoff.md` (mechanical, regenerated by `make handoff`) links the newest narrative, `docs/analysis/<date>-session-handoff.md` | `make handoff` at the end of every session; `tests/unit/test_session_handoff_narrative_pointer.py` | Before editing anything |
| The product owner's decisions (default values, policies, scope) | `docs/19-change-control-log.md`, one `CHG-NNN` row per decision with the owner's words and the date | Hand-written by the pull request that implements or records the decision; a row that records the owner's in-session words (CHG-011, 012, 018, 021 to 026) cites the transcript and time; a row that builds on an earlier decision cites that CHG row or analysis file | Before building anything an owner must approve; before calling anything "undecided" |
| The owner's own words, verbatim, per session | `docs/analysis/<date>/OWNER-DISCUSSION-LOG.md` (from 2026-09-29 on); earlier: `docs/analysis/2026-09-22-decision-register.md` | Hand-extracted from the session transcript (`type: user` records only); the status table at its top is updated by later sessions | When a CHG row is too short, or to check what the owner actually said |
| Technical and method decisions, with the alternatives rejected | `docs/adr/` — one file per decision, superseded never edited | `docs/24-adr-index.md` is generated and checked by `scripts/generate_adr_index.py --check` inside `make validate` | Before changing a default, a failure posture or a policy (AGENTS.md rule 16d) |
| Failure modes listed BEFORE building money, auth or safety code | `docs/analysis/<date>-<work>-failure-modes.md` | Hand-written per work package (AGENTS.md rule 16e) | Before designing the next piece of the same feature |
| Dated incidents and the lesson each earned | `docs/103-incident-learnings.md` (dated entries; the file asks that new ones go at the top) | Hand-written after each incident | After an incident; before adding a gate (see `docs/metrics/defect-discovery-audit.md` for what gates have and have not caught) |
| Measured numbers about quality (coverage, flakes, mutation, defect discovery) | `docs/metrics/` | Each file names the command that produced its number | Before quoting a number about the repo |
| Evidence grades for practices this repository relies on | `docs/evidence/` (see its `README.md`) | Hand-written, dated, graded | Before citing a practice as proven |
| Requirements, acceptance criteria and traceability | `docs/10-`, `11-`, `12-`, `17-`, `18-` | `make fr-completeness` inside `make validate` | When adding or changing a feature |
| Architecture, domain model, API and data contracts | `docs/20-` to `29-`, `docs/architecture/` | `make openapi-check` for the API contract; the rest hand-written | When changing a boundary |
| Threat model, security controls, privacy, retention | `docs/40-` to `49-` | Hand-written; `docs/48-data-retention.md` names the owner approval for each kept datum | Before touching sign-in, money, stored data |
| Test strategy and what each gate can and cannot see | `docs/50-` to `59-`, `docs/analysis/03-enforcement-machinery.md` | Hand-written; the gates themselves are in `Makefile` and `.github/workflows/` | Before adding or loosening a check |
| Release, deploy, rollback, operations | `DEPLOY.md` (how to deploy), `docs/70-` to `89-`, `docs/runbooks/` (one per failure) | Hand-written; `scripts/deploy_drift_check.py` alarms when production drifts from `main` | Before a merge (AGENTS.md rule 18); when something is down |
| Every `make` target and what it does | `Makefile` (the truth), `docs/110-command-reference.md` (the explanation) | `tests/unit/test_makefile_gate_integrity.py` pins the gate targets | When running anything |
| Plans, reviews and analyses from past sessions (read-only outputs) | `docs/analysis/` (dated file names; the live record), `docs/archive/<month>/` (history: superseded prompts and handoffs, kept and still citable) | Moved, never deleted (AGENTS.md, "Where files live") | Only when a detail is needed |
| The 2026-09-28..30 owner discussion, engineering review, bug root causes, harness plan and research | `docs/analysis/2026-09-29/` (start at its `README.md`, which maps the file names; then `NEXT-SESSION-PROMPT.md`) | Copied from the outside evidence folder on 2026-09-30: three files unchanged, the others with a mapping note or reworded citations (listed in that folder's `README.md`); probe scripts and raw reports stayed outside | Planning the harness, fixing the owner's bugs 1–10 |
| Text a future session RUNS (a prompt) | Repository root, `*-ULTRACODE-PROMPT.md` | Superseded prompts move to `docs/archive/` | When told to run one. A prompt is the session's wording, not the owner's; decisions in it are only decisions once a CHG row records them |
| Product description for a reader outside the repository | `README.md` at the root; `docs/study/` for the study write-ups | Hand-written | Writing anything public |
| The factory template this repository was generated from, and its lifecycle scaffolding | `docs/factory/`, `docs/105-` to `111-` (template docs: skills, commands, contract governance, start-here); the discovery docs `docs/01-` to `09-` and the console `docs/00-` | Not maintained beyond the template; `docs/00-factory-console.md` is regenerated by `make next` and is NOT a work status | Rarely; the board and the ADRs are the live sources |
| A numbered `docs/NN-*.md` not named in a row above | The file itself; `docs/adr/0034-docs-numbering-scheme-and-ranges.md` gives the theme of each number range (111–124 is a collision-overflow range of mixed origin, not a theme) | Varies by file: check its `git log` date before trusting it | When its theme matches your question |
| An agent's private notes (memory) | Outside the repository, under `~/.claude/projects/<repo>/memory/` on one machine | Written by that agent; nobody else can read it | Never rely on it. Anything the repository needs goes in a file above |

## Where NOT to look for a decision

- `docs/00-factory-console.md` is the factory router's view, regenerated
  wholesale by `make next`. Anything typed into it is lost on the next run.
- A `*-ULTRACODE-PROMPT.md` at the root, or a handoff, records what a session
  intended. It becomes a decision only when `docs/19-change-control-log.md`
  has the row.
- `CHANGELOG.md` was last edited 2026-08-10; `git log` on `main` is the record
  of what shipped.

## How this map stays true

The two tables below are generated from the tracked tree (`git ls-files`) by
`python3 scripts/check_docs_map.py` and checked by
`scripts/check_docs_map.py --check` inside `make validate`: a tracked top-level
file or folder added, renamed or removed under `docs/`, a top-level file's first
heading changed, or a folder's index file added or removed, without re-running
the script, turns `make validate` red. A new file counts once it is `git add`ed. The hand-written table above is checked only by readers; when a row stops
being true, fix the row in the same pull request that made it false.
