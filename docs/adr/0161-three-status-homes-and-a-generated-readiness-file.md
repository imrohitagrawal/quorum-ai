# ADR-0161: Three status homes, and a readiness file generated from production

## Status

Accepted — 2026-10-11, package B of `docs/analysis/2026-10-11-how-we-work-review.md`. The product
owner chose the readiness wording "Facts plus a verdict" (CHG-040 (d)). The owner delegated what
happens to the old status documents to the session (CHG-040 (e)); the choice below is the
session's, and CHG-041 records it.

## Context

On 2026-10-11 a reader with no project memory, on a copy of `main` at `c894f78`, answered "what is
live, what is open, is it ready?" from the repository. It got 9 of 19 expected facts right. Its
sources disagreed with each other:

| Source | What it said |
|---|---|
| `docs/session-handoff.md` | build `2a6959a` (production ran `c894f78`), 9 open issues (GitHub had 4) |
| `docs/95-production-readiness-review.md` | "Decision: **Go**" (2026-06-21) |
| `docs/73-release-evidence.md` | "No-go for production release" |
| `docs/factory-status.md` | every gate "Draft"; "no-go" |
| `docs/17-requirement-registry.md` | all 31 rows "Draft" |
| `docs/74-release-checklist.md` | every cell "TBD" |

## Decision

1. **Three kinds of status, each with one home,** named in `docs/README.md`:
   - **delivery:** the board, `docs/65-open-work.md`, and GitHub. The board-versus-GitHub check
     (ADR-0162) keeps them in step;
   - **product readiness:** `docs/product-readiness.md`, generated by `make readiness` from
     production's `/status` and `/ready`. `make handoff` regenerates it;
   - **decisions:** `docs/19-change-control-log.md` and `docs/adr/`.
2. **The readiness file states facts plus a verdict.** It gives the time and build it was
   generated from; what production has in effect; what is built but switched off; and the
   verdict. The verdict is "Ready" only when live execution is on, `/ready` reports `ready` with
   no reasons, and the global spend ceiling is not reached (amended after review round 1). Otherwise it is "Not ready", with the reasons. It says how to get the current
   value, because production moves after every merge. A release decision is a CHG row, not this
   file.
3. **The old status documents,** decided by the session under the owner's delegation:
   - `docs/17` and `docs/18` stay, because the blocking requirements gate reads them. Each gets a
     banner pointing at the three homes. The `docs/17` Status column is relabelled as the
     draft status each row was given when it was added, and its four false "Not started" cells in
     `docs/18` are corrected;
   - `docs/95`, `docs/74` and `docs/73` get a banner: they are named by configuration, and
     archiving them breaks `make validate`;
   - `docs/factory-status.md` gets a "not maintained, do not update" banner. No script reads it,
     but 21 skill files named it at the cut-off (`git grep -l factory-status b66b107 -- .agents/skills`), 18 of them
     checklists; archiving it would send them to a missing file, and a session could recreate it.
     Of the three skill files that listed it as an output, two now say not to update it, and the
     third (`session-continuity-manager`) now writes its notes to the narrative handoff;
   - `116-signoff-record.md` moves to `docs/archive/2026-10/116-signoff-record.md`. Nothing reads it. Two skill
     files and four documents named it: `docs/91` and the design handoff now point at
     `docs/19-change-control-log.md`, and the others drop the line.

## Rejected alternatives

- **Readiness inside `docs/session-handoff.md`.** That file is a session snapshot; a reader
  looking for readiness would not look there, and its other values are about the session.
- **Keep `docs/17`'s 31 statuses current by hand.** Nothing checks them, and nobody owns them.
  They went stale once already.
- **Archive `docs/95` and `docs/74`.** Measured: `make validate` fails with "Missing required file".

## Consequences

- The readiness file is true when generated and ages after. It says so, with the time and build.
- A fresh reader still cannot see production without the network. The file is the best a
  repository can hold.
- `docs/analysis/2026-10-11-one-status-failure-modes.md` lists what this can get wrong.

## Amendment after review round 1 (2026-10-12)

Four gaps a review found, each pinned by `tests/unit/test_one_status_review_round_1.py`:
- The verdict also needs `/ready`'s `live_readiness` to say the global spending ceiling is not
  reached, and to carry its `reasons` list and its ceiling field. When the ceiling is reached, new
  runs are answered by the local simulation, so the verdict is "Not ready". A `/ready` without
  those fields is "Not ready" too, with a reason naming the missing field.
- Only the default production URL is called production. A file made with `--base-url` names that
  server by its URL, and its verdict line says it is not production.
- With live execution off, the judge, page fetching and page reading are listed under "Built and
  switched on, but idle while live execution is off", not as in effect: no run reaches them.
- The file embeds the two responses it was made from, in a fenced JSON block. A test re-renders
  the file from that block and needs an exact match, so a verdict typed by hand, without changing
  the embedded responses, fails. A forgery that edits both the responses and the verdict passes:
  the block proves the text matches its input, not that the input came from production.
