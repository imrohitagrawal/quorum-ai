## Why it is not one pull request (measured)

- **Money:** the estimator refuses one slot (`_cost_components` raises
  `ValueError('model_slots must contain between 2 and 4 slots')`), builds a
  FIXED `by_stage` list of four rows plus the judge, equalises the two
  debate rows by index (an `IndexError` on a two-row list), and the measured
  receipt (`build_measured_breakdown`) always emits all four stage rows at
  `$0` — so a quick estimate AND a quick receipt need their own branch, with
  a cardinality test on both (rule 6b), or the estimate and the receipt do
  not pair.
- **The run path crashes before any debate:** `panel_size_word(1)` raises
  at the initial-answers stage detail; the debate and synthesis prompts call
  `panel_size_word`/`all_models_phrase`; the status machine has no
  `INITIAL_ANSWERS_RUNNING -> COMPLETED` edge. A quick run skips two stages
  and needs the edge and a SKIPPED stage state the live view already labels.
- **The request shape is silently wrong today:** the request base has no
  `model_config`, so a client posting `mode: "quick"` is accepted as a panel
  request (extra fields ignored). Adding `mode` to the shared base changes
  both request schemas in `openapi.yaml` (regenerate) and what schemathesis
  fuzzes on `/estimate`; the validator and the estimator branch must ship in
  the same commit or a fuzzed `mode: "quick"` with a one-item list reaches
  the estimator's raise as a 500.
- **The token:** ADR-0123 binds a shape STRING, so `"quick"` fits; the mint
  and the verify ends must both learn the mode or every quick token is
  refused and consumed.
- **The UI:** no result-view renderer shows a single answer today (only the
  transcript and hidden live panels); a new `setProse` surface is swept by
  the rendering-invariants gate; four-stage assumptions sit in the live
  strip, the receipt's pipeline order, the cost-gate meta line and the
  "Initial answers × 4" copy; the degraded banner's copy at `total=1` reads
  "None of the 1 models…"; thirteen e2e files wait on
  `#result-verdict[data-consensus]`; the existing views must stay
  byte-identical (rule 13e), proven by an outerHTML diff on the golden
  fixture.
- **Docs and gates:** ADR-0124, CHG-013, an FR and an AC with traceability
  rows, the board needle (polarity trap below), AGENTS.md's invariant-spec

## The two decisions not in §4 (PROPOSED — AWAITING OWNER)

1. **What the page shows of the judge.** The owner's purpose (D1): "Judge
   will help user understand whether the answer that model give is how much
   accurate." Today the browser is BANNED from reading any judge field
   (`tests/unit/test_evaluation_projection_has_no_judge.py` refuses
   `judge_status` and friends in `app.js`); the only judge-gated surface is
   the trust score, whose composite includes `agreement_ratio` (1.0 at N=1)
   and three synthesis-only signals scored as absent. So at N=1 the trust
   surface is either inflated or full of "not surfaced" shortfalls for stages
   that never ran. Showing the judge's verdict plainly means opening that
   gate deliberately, or defining a quick-only trust shape. Also the judge's
   shared system prompt says "You score one multi-model answer" and requires
   `disagreement_preserved` "in the synthesis"; changing it changes every
   production run's judge (`JUDGE_PROMPT_ID`) — its own decision.
2. **What "agreement" and "safety notices" mean at N=1.** The projection
   serves and the run store persists `agreement 1 of 1` for a single answer
   (`build_agreement_and_positions([one], [], None)` returns aligned=1,
   total=1); the only high-stakes carrier on a result is
   `FinalSynthesis.high_stakes_notice`, which a quick run never produces, so
   "keeps the safety notices" (the approved plan) has no carrier and needs a
   new field populated from the create-time warnings.
