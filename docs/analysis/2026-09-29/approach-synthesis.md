# Synthesis: the development approach for Quorum's autonomous agent harness

2026-09-29. Written as a principal engineer. Based ONLY on the seven research reports in this folder. Each claim cites the report (by lens name) and, where it rests on an outside source, the URL that report says it opened. Anything a report marked UNVERIFIED stays UNVERIFIED here. I ran no new commands against the repo; every repo fact below is the measuring lens's, not mine.

Reports used (same folder): `spec-driven-ai.md`, `acceptance-bdd-tdd.md`, `quality-engineering.md`, `security-privacy.md`, `delivery-operations.md`, `ai-evals.md`, `enforcement-mechanics.md`.

---

## 0. The answer in six lines

1. **Spec-driven development is the right backbone, but "the best approach" is not supported by the evidence.** No report found a study showing it beats the alternatives. Thoughtworks rates it "Assess" (spec-driven-ai). As shipped by today's tools it is a planning format that never runs the app (spec-driven-ai: Spec Kit `tasks-template.md:12` makes tests optional).
2. **Quorum already did spec-first and TDD, and the owner still found 33 of 64 journey and message defects.** The acceptance criteria stop at AC-052. The criteria-to-test map has 200 test ids and 0 of them appear in any test (acceptance-bdd-tdd). So "more spec" is not the fix. The fix is: examples the owner approves, run as tests the builder cannot edit, plus testing that uses the running app.
3. **The recommended approach combines eight practices**, with three of them as equal partners to the spec rather than add-ons: product-critique testing (exploratory, usability, accessibility), eval-driven development for the AI parts, and continuous delivery with a check after each deploy.
4. **Nothing is enforced today.** 30 of the last 30 merged pull requests were written and merged by the owner's account with 0 reviews; branch protection needs 0 approvals; CODEOWNERS is an invalid placeholder; `.claude/settings.json` is not in git (enforcement-mechanics). The first job is a separate agent identity plus required owner review on a small set of paths. Hooks give fast feedback; they do not enforce.
5. **The order:** make the owner's review binding and fix two present-day defects first, then build the signed-in real-backend test launcher, then run one exploratory session on today's build, then take the owner's nine bugs through the new loop, then everything else.
6. **Compared with the earlier 7-step proposal: the earlier proposal is a subset of this one**, with three real contradictions (§4): the hooks file is not tracked and hooks are not enforcement; "every must maps to a check or is deleted" would delete the only practice that has found the owner's class of bug; and spec-driven is not "the" best approach on its own.

## 1. The recommended development approach

### 1.1 The practices it combines, and what each one contributes

Terms, defined once:
- **Spec-driven development (SDD):** write a structured spec before the agent writes code.
- **Acceptance-test-driven development (ATDD):** the acceptance tests are written, from the owner's intent, before the feature is built.
- **Behaviour-driven development (BDD) / Specification by Example (SbE):** requirements written as concrete Given/When/Then examples, agreed before the build and run as tests.
- **Double-loop TDD:** a failing acceptance test (outer loop) drives many small unit-test cycles (inner loop).
- **EARS:** fixed sentence patterns for requirements, e.g. "WHEN … THE SYSTEM SHALL …" and "IF … THEN THE SYSTEM SHALL …".
- **Eval:** a set of inputs plus a grader, run repeatedly to get a pass rate, for output that is not the same twice.
- **SLO (service level objective):** a target for a measured service number.

Cross-cutting, and the reason the harness is shaped the way it is: **the builder must not grade itself.**
- ImpossibleBench: frontier models cheated on about half of impossible tasks; read-only tests restored honest performance, notably for Claude (spec-driven-ai, enforcement-mechanics → https://arxiv.org/abs/2510.20270).
- METR: telling models not to cheat left cheating at 70–80% (enforcement-mechanics → https://metr.org/blog/2025-06-05-recent-reward-hacking/).
- AI-written tests tend to check what the code does, not what it should do (acceptance-bdd-tdd → https://arxiv.org/abs/2410.21136).
- Anthropic's planner/builder/evaluator harness found a separate evaluator driving the running app was needed, and that "Claude is a poor QA agent" until tuned to be sceptical (spec-driven-ai, Rajasekaran, 24 Mar 2026).

### 1.2 The stage-by-stage workflow

Two paths, so small changes stay light (spec-driven-ai: change-only specs; Böckeler saw Kiro turn a small bug into 16 criteria):
- **Light path:** a fix that changes no journey, limit, message, stored data, outbound call, prompt or session behaviour. It needs a failing test that a non-builder wrote or approved, then the fix, then stages 5 and 7. No spec change.
- **Full path:** everything else, and anything in the high-risk classes (money and limits, sign-in and sessions, personal data, AI output).

"Done" is set only by CI or the evaluator, never by the builder saying "tests pass" (spec-driven-ai: Spec Kit's own line "completion claims are not evidence").

### 1.4 What is overkill for a one-owner product — leave it out

| Leave out | Why (lens) |
|---|---|
| Adopting Spec Kit or Kiro wholesale | Quorum's process is already heavier; take four pieces only: clarification markers, the bug-fix "SHALL CONTINUE TO" form, spec-line-to-test links, the sprint contract (spec-driven-ai) |
| Cucumber and step-definition glue | The evidence supports the examples and the conversation, not the tool; the glue layer adds the upkeep cost the SANER 2018 survey reports. Plain Given/When/Then in Markdown plus the example id in each test title (acceptance-bdd-tdd; this is a judgement, no source compares the two) |
| A gate proving each unit test was written first | Order did not matter in the best-controlled study (acceptance-bdd-tdd) |
| Canary, blue-green, feature-flag platform, A/B experiments, a staging environment | Fly offers neither canary nor blue-green for machines with volumes; one machine; too little traffic (delivery-operations) |
| Burn-rate paging and an on-call rotation | Needs steady traffic; the repo's own probe already skips quiet windows (delivery-operations) |
| DORA metrics as targets | They score Quorum as healthy today while the owner finds bugs; DORA itself warns against Goodhart's law (delivery-operations) |
| Pact contract testing | Not for this shape of API; extend the existing fake-reply check instead (quality-engineering) |
| OWASP SAMM per feature | An organisation assessment; quarterly self-check at most (security-privacy) |
| ASVS Level 3 beyond automatic deletion (14.2.7) | L1 everywhere, L2 for sign-in, OAuth, authorization, money limits and data protection (security-privacy) |
| Chaos testing in production; signed-in checks in production | Paid runs and real accounts; keep faults in-process and signed-in journeys pre-merge (quality-engineering; delivery-operations) |
| Expanding the mutation gate | Already strong; add only the short targeted list (quality-engineering) |
| A production environment reviewer | Conflicts with "release when green"; the owner's gate is code-owner review on intent paths instead. **This is a decision; record it in an ADR** (enforcement-mechanics raised the conflict; the choice here is mine) |

## 5. Known criticisms, and how the design guards against them

| Criticism | Evidence it is real | Guard in this design |
|---|---|---|
| **Spec drift** — the spec is written once and left behind | Böckeler's "spec-first" level; Quorum's criteria stop at AC-052; W7 PRs #518–#522 edited no requirement document; `docs/41` and `docs/43` unchanged since the initial commit (spec-driven-ai, security-privacy) | Specs change with every feature PR (change-only); the example-id link check fails when an example has no test or a test names no example; the data inventory is checked against the real schema; the decisions log is never archived and is an owned path |
| **Waterfall** — heavy documents up front, the same process for every change | 15 required documents, 127 files in `docs/`, 791-line AGENTS.md; Kiro turned a small bug into 16 criteria (spec-driven-ai) | Light path for small fixes; Example Mapping limits (split a story with many rules, 3–5 key examples per rule); one journey slice per PR (median PR is 485 lines today, delivery-operations); AI specs deliberately stay open until outputs are read (criteria drift, ai-evals → https://arxiv.org/abs/2404.12272) |
| **Agents grading themselves** | ImpossibleBench, METR, Konstantinou; Anthropic's harness found self-evaluation over-praises | Tests and labels written by a non-builder and read-only to the builder; a separate sceptical evaluator on the running app; a different model family (Codex) in each fan; findings reproduced by another agent; "done" set only by CI or the evaluator; separate GitHub identity so "owner-approved" cannot be self-applied |
| **Gameable checks** | The traceability check passed after all 52 criteria were replaced with two lines (engineering review via acceptance-bdd-tdd); judges pass "Thought process:"-only outputs (ai-evals → https://arxiv.org/abs/2507.08794); the hook regex let 7 of 12 bypasses through | Check structure, not text presence; every "none missing" check paired with a count > 0; tests must fail on the base commit; targeted mutants the acceptance tests must catch; graders must fail known-bad outputs; the checks themselves live on owned paths |
| **Process bloat** | 11,800 words of rules per session; "Bloated CLAUDE.md files cause Claude to ignore your actual instructions!" | One-page must-list, each line naming its mechanism; overkill list (§1.4); advisory checks promoted only on measured yield after a month; judgement rules that nobody follows are deleted at the monthly review |
| **Cost** | Anthropic's full harness: $124.70 and ~3 h 50 min vs $9 and 20 min for a single agent (spec-driven-ai) | Critique fan per batch, not per PR; live evals only on AI-path changes with a cap and an owner-set budget; production checks are free by design |
| **Slow, flaky end-to-end tests** | Larger tests are more flaky (Google, 4.2 million tests, acceptance-bdd-tdd) | Most examples at API level; one or two signed-in browser tests per journey; business-language assertions through one page-object layer |
| **Agent critique produces false positives** | Agent-written property tests: 56% valid bugs; LLM usability review found 21.2% of expert issues (quality-engineering) | Separate reproduction before any finding counts; ≥3 evaluators; owner's short pre-release session kept |
| **The owner becomes the bottleneck again** | A separate identity puts the owner back in the loop for owned paths (enforcement-mechanics) | The owned set is kept small (intent, gates, acceptance tests); everything else merges on green; the owner's in-loop duties are: question cards, approving intent files, deciding spend, accepting leftover risk |
| **Measuring the wrong thing** | DORA scores Quorum as healthy today (delivery-operations) | The primary quality measure is escaped defects by who found them, per class; no metric is set as an agent target |

## 6. Limits of this synthesis

- No report found a study of any of these practices inside an autonomous agent harness. This is a design built on evidence about the parts; it should be judged by the monthly "who found the bugs" count.
- UNVERIFIED items that decide design details, each with the check a lens named: code-owner review with 0 required approvals (scratch repo); whether worktree sessions load project hooks (`/hooks` in a worktree); what production actually runs (`fly ssh console -C "pip freeze"`); Fly `rolling` with one machine and a failing health check; whether one simulated production run could push a real user over a cap; the source-fetcher trifecta (loopback test); whether a managed settings file applies on a personal plan.
- The escaped-defect budget is the delivery lens's own proposal with no outside evidence.
- Several effect sizes are self-reported or vendor-reported (Microsoft SDL, Adzic's survey, Veracode) and are used as direction, not as numbers to plan against.
