What Quorum AI is, what problem it solves, how it works, and the words we use.

? What is Quorum AI?

Quorum AI is a research-synthesis tool. You type one question, it runs that question against four large language models (LLMs) in parallel, has a separate moderator model critique those answers across two debate rounds, and produces a single answer split into five sections: consensus (what all models agree on), disagreement (where they diverge), source support (what backs each claim), uncertainty (what is not settled), and recommendation (a practical takeaway).

A repo (short for repository) is a project's complete file history stored on GitHub — think of it as a version-controlled folder that every collaborator can read and contribute to. The Quorum AI repo is at github.com/imrohitagrawal/quorum-ai.

The product is designed for decision support, not for automated decisions. The output is meant to help you think more clearly, not to replace your judgment on high-stakes matters like medical, legal, or financial questions.

Picture it in real life

Imagine calling four independent research assistants, giving each the same brief, asking them to mark where they agree and disagree, and then having a senior editor write a one-page summary that surfaces the uncertainty. That is the workflow — except the assistants are LLMs and the editor is also an LLM.

? What problem does it solve?

If you want a well-rounded answer to a non-trivial question today, you typically open four different AI chatbots, type the same prompt into each, and manually compare the responses. That process is tedious, easy to skip (most people ask one model and stop), and offers no structured view of where the models agree, disagree, or hedge.

Quorum AI automates that process: the four calls happen in parallel, the cost is shown upfront, and the synthesis enforces that disagreement and uncertainty are preserved in the final output — not smoothed over.

The four model slots (model_slots.py) are the constant source of truth. Each slot selects a different vendor — OpenAI, Anthropic, Google, or NVIDIA — so a single run covers four independent training runs and four independent safety fine-tuning passes. The debate module (debate.py) then asks a separate moderator model to critique all four answers, which catches the "all models confidently saying the same wrong thing" failure mode.

Picture it in real life

Before making a hiring decision, a good manager does not rely on one interviewer's notes. They gather multiple perspectives, note where opinions converge, and flag the disagreements for further discussion. Quorum AI applies that instinct to AI-assisted research.

? How does the AI design work? Why four models?

The four models are selected from four different vendors by design. Different vendors train on different data, apply different safety fine-tuning, and have different failure modes. Running one model per vendor gives you four independent perspectives on the same question. Two debate rounds are then used to surface the disagreements: a separate moderator model reads all four answers and writes a critique, then refines it in a second round. The four answer models are each called once and do not read each other — peer critique between them is in development.

A model is a specific AI system identified by a string like openai/gpt-4o-mini. The string has two parts: the vendor (who trained and hosts it) and the version (which training run). A token is the unit LLMs bill on — roughly ¾ of a word for English text. Providers charge per 1,000 tokens of input and output.

An API key is a secret string that authenticates your application to an external service (like ). In Quorum AI, the operator's API keys are stored server-side in Fly secrets — they never leave the server boundary and never appear in browser code, logs, or error responses.

Picture it in real life

Four independent weather stations each forecast tomorrow's temperature. You do not take one station's word — you compare all four, note where they converge (it will rain) and where they diverge (high of 18 vs 22 degrees), and then decide based on the spread. Four models are the minimum to get meaningful disagreement; fewer than four collapses to a single-opinion echo.

? What do you mean by "ephemeral"?

Quorum AI does not persist query results to a database by default in the current slice. When you refresh the page, the result is gone. This is a deliberate product posture: a research/synthesis tool is not a chat log. The architecture docs note that a durable run-history store (FR-014 / S1) was added for operator metrics — run metadata, cost, and evaluation scores are now written to run_history_store.db — but query text, model outputs, and synthesis prose remain session-scoped and are not part of the stored history.

A commit is a snapshot of the repository at a point in time. Each commit has a short SHA (like 9555701) that uniquely identifies it. You can browse the commit history with git log on the command line, or on GitHub.

Glossary — key terms defined

API
Application Programming Interface — a structured way for one piece of software to call another. Quorum AI's API is a set of HTTP endpoints (like POST /v1/query-runs) that the browser calls to start a query run.
API key
A secret string that proves your application is authorised to use an external service. Kept server-side; never sent to the browser.
Commit
A snapshot of the repository's files at a point in time. Identified by a short SHA (e.g. 9555701).
Model
A large language model identified by a vendor/version string, e.g. openai/gpt-4o-mini. Different vendors = different training data and safety fine-tuning.
Token
The unit LLMs bill on — roughly ¾ of an English word. Costs are quoted per 1,000 tokens.
Repo
Short for repository — the project's file history on GitHub. URL: github.com/imrohitagrawal/quorum-ai.
Synthesis
The final output section that combines all four model answers into consensus, disagreement, source support, uncertainty, and recommendation.
Debate round
One cycle where a separate moderator model reads all four answers and writes a critique. Two rounds are run per query.
Query run
A single execution of the full workflow: estimate → four initial answers → two debate rounds → synthesis. Identified by a query_run_id.
Source
A web page or document that a model cites to support a claim. Shown next to the model's answer.
FastAPI
A Python web framework used to build Quorum AI's backend. It generates API docs, validates input with Pydantic, and serves async endpoints.
SQLite
A file-based database. Quorum AI uses two SQLite files for durable storage: feedback_store.db (cost events) and run_history_store.db (terminal run metadata).
CSP
Content Security Policy — a browser security header that restricts which scripts, styles, and connections a page is allowed to load. Quorum AI uses a strict CSP to prevent injection attacks.
CSRF
Cross-Site Request Forgery — an attack where a malicious site tricks your browser into making a request you did not intend. Quorum AI defends against this with a per-session CSRF token bound to a signed cookie.
Fly.io
The cloud platform where Quorum AI is deployed. A containerised FastAPI service runs on Fly's edge network, fronted by Cloudflare DNS.
Cloudflare
The DNS and HTTPS provider for Quorum AI's custom domain (quorum.stackclimb.com). It terminates TLS and proxies requests to Fly.io.
A unified API gateway for multiple LLM vendors. Quorum AI calls , which routes to the selected model's actual vendor (OpenAI, Anthropic, Google, or DeepSeek).
Tavily
A web-search API used as a fallback when 's built-in search is unavailable. Gated on a TAVILY_API_KEY environment variable; absent by default.
Sentry
Error-tracking software. When configured (via SENTRY_DSN), unhandled exceptions and performance traces are reported — with all query text and LLM responses redacted first.
Prometheus
A monitoring system that scrapes metrics from Quorum AI's /metrics endpoint. Used by the ops dashboard at /ui/ops.
SLO
Service Level Objective — a target the product is held to. Quorum AI declares SLOs for availability (99%), 5xx rate (<1%), and query latency (P50 ≤ 45s, P95 ≤ 120s, hard timeout 180s).
Trust score
A weighted composite of deterministic quality signals (citation coverage, agreement ratio, uncertainty surfaced, etc.) that measures how trustworthy a run's output is. Suppressed to "unverified" while citation support has not been verified.
BYO key
"Bring Your Own" key — a user-supplied API key stored server-side for their session, allowing higher usage limits. Controlled by OPENROUTER_LIVE_EXECUTION_ENABLED and the operator's key.
Simulation mode
A fallback where the app produces templated, deterministic outputs instead of calling live LLMs. Active when no key is configured or OPENROUTER_LIVE_EXECUTION_ENABLED is false. The /ready endpoint surfaces the state so the UI can show a banner.

Working with the tools

Which model to pick, what each cost tier means, how the skills and config system work, and where your keys live.

? Which model should I pick for my query?

You do not need to pick — the four default slots already cover four vendors and a wide price/quality range. The defaults are:

  • openai/gpt-4o-mini — fast, cheap, good general-purpose model
  • anthropic/claude-haiku-4.5 — fast, strong at analysis and critique (also the default debate writer)
  • google/gemini-2.5-flash — fast, Google's lightweight frontier-class model
  • deepseek/deepseek-chat-v3.1 — open-weight, cost-efficient, strong reasoning

If you want to customise, the model catalog endpoint GET /v1/models/defaults lists every available option with pricing. The cost estimate screen updates live as you change slots, so you can see the dollar impact before committing.

The cheapest_per_vendor function filters out :free models to avoid a known Step-A bug where "free" models produced templated output. The server-side estimate in costs.py re-prices against the catalog on every call — the client mirrors the arithmetic client-side for responsiveness.

You send all four and let the group decide, rather than trusting one person's pick. ? What are the cost tiers?

Quorum AI uses a three-band cost guardrail (implemented in costs.py):

  • ALLOW — estimated cost ≤ $0.15. Run proceeds with one click.
  • REQUIRE CONFIRMATION — $0.15 < estimated cost ≤ $0.25. You must click "Confirm" to proceed. A confirmation token (bound to your account, valid 5 minutes) is required.
  • BLOCK — estimated cost > $0.25. Cannot run, regardless of confirmation. There is also a per-account daily cap of $0.20 in any rolling 24-hour window.

The estimate is a realistic point figure — it models each of the seven billed calls (4 initial answers + 2 debate rounds + 1 synthesis × 5 sections) using actual token counts and cached per-model prices. The guardrail keys off a fail-safe upper bound (pricing initial-answer output at the enforced 2000-token cap), so a run's output cost is bounded by the figure it was waved through under. The bound also prices the Layer-B judge when one is configured (#265). It does not bound the INPUT side — the system-prompt and web-search context sizes are assumptions, not enforced caps — so the figure is the worst case the run is priced at, not a guarantee it cannot be exceeded.

A token is the billing unit LLMs use. Roughly 4 characters of English text ≈ 1 token. A 500-word query is ~375 tokens; a 500-word model answer is ~375 tokens of output. Providers charge per 1,000 tokens (e.g. $0.00015 per 1K input tokens for gpt-4o-mini).

● Built
In your project

The costs.py module exports CostEstimationService which computes estimated_cost_usd, max_cost_usd (the fail-safe bound), and a CostBreakdown partitioned both by model (four slot rows + one "Debate + synthesis" row) and by stage (initial answers, debate round 1, debate round 2, synthesis). The breakdown re-sums to the quantized total exactly (largest-remainder / Hamilton method). A daily cap of $0.20 is enforced against the durable SQLite feedback store, not the in-memory ring buffer, so trickle attacks over hours are also bounded.

The confirmation token is like a signed receipt — it expires in 5 minutes and is bound to your room number so you cannot replay someone else's receipt.

? How do skills and config work?

Skills are bundled playbooks for specific tasks (TDD, e2e testing, architecture review, security review, etc.) that are loaded on demand. They are not code libraries — they are instruction sets that tell the agent how to approach a particular kind of work. The skill router (make skill-route) recommends which skill to use for the next missing artifact.

Configuration lives in environment variables read at process start by product_app.config.Settings (a Pydantic BaseSettings class). The critical ones are:

  • OPENROUTER_API_KEY — the operator's LLM provider key. Server-side only.
  • OPENROUTER_LIVE_EXECUTION_ENABLED — must be true for live LLM calls; otherwise the app runs in simulation mode.
  • TAVILY_API_KEY — enables the real web-search fallback. Absent by default (CI stays hermetic and free).
  • QUORUM_EVAL_JUDGE_API_KEY — enables the optional LLM-as-judge for evaluation. OFF by default.
  • RUNTIME_ENVIRONMENT — one of local, staging, production. Production enforces stricter defaults.
  • QUORUM_TOKEN_SECRET — a stable secret for signing confirmation tokens. Required in non-local environments.
  • SESSION_RATE_LIMIT_PER_MINUTE — per-IP rate limit override for hermetic test lanes. Must be unset in production (the startup validator refuses to start otherwise).

Configuration is loaded once at process start. There is no per-request config reload. The .env file is in .gitignore — never commit it.

? Where are my API keys? Are they safe?

Operator-owned keys (, Tavily, the eval judge) are stored in Fly secrets — environment variables injected at container start by Fly.io's secrets manager. They never appear in source control, never appear in API responses, never appear in logs, and never reach the browser. The codebase has explicit redaction tests in tests/security/test_release_security_redaction.py that assert secret-shaped strings never appear in any error log.

The Field(default="", repr=False) annotation on key fields in config.py ensures that printing a Settings object never leaks the key value (the repr=False flag suppresses it from the Pydantic repr; the empty default means a missing key is an empty string, not None).

Architecture and decisions

The stack, why it is this not something else, the components, the debate-synthesis design, and the architectural decision record trail.

? What is the tech stack?

Quorum AI is a modular monolith — a single deployable FastAPI service with explicit internal boundaries. The components are:

  • FastAPI (Python 3.13) — the web framework and API layer
  • SQLite — file-based database for durable run metadata and cost events
  • — unified LLM API gateway (routes to OpenAI, Anthropic, Google, DeepSeek)
  • Tavily — web-search fallback (gated on TAVILY_API_KEY)
  • Fly.io — container hosting with one process, one worker
  • Cloudflare — DNS + HTTPS termination + DDoS protection
  • Prometheus — metrics exposition at /metrics
  • Sentry — error tracking (gated on SENTRY_DSN)
  • uv — Python package manager and runner (replaces pip + venv)

Frontend: vanilla HTML + JavaScript + CSS (no framework). The single page at /ui is rendered from templates/workspace.html with server-side data islands injected at render time.

? Why not a browser-only app? Why not microservices?

Two alternatives were explicitly considered and rejected in the architecture docs:

Browser-only (four independent chatbot integrations): This would require the browser to hold API keys for every vendor, making cost control weak (a malicious tab can rack up charges), observability impossible (no server-side telemetry), and secret rotation a user burden. The current design keeps all provider credentials server-side.

Full microservices from day one: The first vertical slice needs correctness, safety, and cost discipline before distributed operational complexity. A modular monolith preserves internal seams (auth, orchestration, providers, safety, persistence, observability) so the orchestration worker can be extracted later if provider volume or latency requires it — without rewriting the whole system.

Anonymous execution: Rejected by FR-001. Anonymous users cannot start provider-consuming work because it creates abuse and cost risk. Every execution endpoint requires a session cookie.

? How does the debate-synthesis design work?

The query workflow has seven stages:

  1. Initial answers — four models called in parallel, each with optional web search. Each call is bounded by a per-call timeout (default 8 seconds) and a hard 2000-token output cap.
  2. Debate round 1 — a separate moderator model reads all four initial answers and writes a critique focused on disagreement, weak support, and missing reasoning.
  3. Debate round 2 — the same moderator refines that critique, focusing on the strongest residual disagreements. The four answer models are not called again.
  4. Synthesis — five independent calls (one per section: consensus, disagreement, source support, uncertainty, recommendation), each re-sending the full context.

The full pipeline has a 180-second hard wall-clock deadline. If it expires, the run terminal state is timed_out and every completed stage's output is returned with a visible missing-step explanation. A run that partially completed is never presented as fully successful.

The synthesis output is deliberately structured: consensus (aligned findings), disagreement (material divergences), source support (citations), uncertainty (what is not settled), and recommendation (a practical next step). High-stakes recommendations are framed as decision support only.

Quality, security, operations

Testing approach, automated checks, security model, how to deploy and verify a release.

? What is the testing approach?

Quorum AI runs a full test pyramid. The make test target runs all suites:

  • Unit — module-level tests (tests/unit/) for providers, costs, debate, synthesis, evaluation, auth, config, model slots, redaction
  • Integration — multi-module flows with a FastAPI test client (tests/integration/)
  • Contract — openapi.yaml must match app.openapi() byte-for-byte (tests/contract/test_openapi_contract.py). Mutated schemas are detected.
  • E2E — end-to-end workflows driven by Playwright (tests/e2e/) including rendering invariants (no raw Markdown in the DOM), visual snapshots, degraded-banner detection, and the trust-score surface
  • Security — redaction contract tests (tests/security/test_release_security_redaction.py) that assert secret-shaped strings never appear in error logs
  • Performance — hermetic latency samples in CI (perf-sample.yml) feeding an advisory perf gate
  • Accessibility — axe-core checks in the e2e suite

The e2e suite is timing-sensitive (the catalog API can return 403 mid-session), so it is designed to be re-run on single-test flakes. The flaky test register is at docs/56-flaky-test-register.md. A full flake scan (960 runs) measured 0 failures (run 29911231157, 2026-07-22).

Evaluation testing (FR-015, NFR-011, NFR-012): Layer-A (deterministic signals) is tested as pure unit code; Layer B (LLM-as-judge) is never called for real in any test — StubEvalJudge is used, and the key gate, strict-JSON contract, and malformed-response-yields-no-verdict paths are exercised against the stub. Neutrality is proven with a seam spy: judge OFF makes zero providers.call_with_prompt invocations and yields a TrustScore identical to the stub-ON case.

? What is the security model?

Quorum AI's security model is documented in docs/40-threat-model.md and docs/41-security-controls.md. The key controls:

  • Authentication: Opaque browser session cookie + CSRF token. No passwords, no email, no account creation. Sessions are issued by GET /v1/session and expire automatically.
  • Authorization: Every execution and result endpoint requires a valid session. Results are scoped to the session's account_id — cross-account access returns 404.
  • Secret isolation: App-owned provider keys (, Tavily, eval judge) are stored in Fly secrets, never in source control, never in API responses, never in logs. BYO keys are server-side only and session-scoped.
  • Redaction: Every error log strips API keys, session tokens, and raw model output. The redaction contract is pinned by tests/security/test_release_security_redaction.py.
  • Content Security Policy: Strict CSP with script-src 'self' 'unsafe-inline' (required for the inline CSRF token injection — a TODO is to migrate to a nonced approach). base-uri 'none' and form-action 'none' prevent injected base tags and form submissions. No CORS middleware — same-origin only.
  • Cost guardrail: Three-band system (ALLOW / REQUIRE_CONFIRMATION / BLOCK) plus a per-account daily cap. Confirmation tokens are HMAC-signed, account-bound, and single-use with a 5-minute TTL.
  • Privacy: Pre-submit warnings for sensitive/private data and high-stakes decision support. The MVP cannot claim sensitive-data safety until provider data-processing terms are finalised.
  • Production validation: validate_production_environment() refuses to start if SESSION_COOKIE_SECURE is false, the legacy header is enabled, the rate-limit override is set, or QUORUM_TOKEN_SECRET is missing.

? How do I deploy and verify a release?

Deployment is via Fly.io. The standard flow:

  1. Push to main triggers the GitHub Actions CI pipeline.
  2. All gates must pass: unit, integration, contract, security, e2e, performance.
  3. On merge to main, the deploy.yml workflow builds and deploys the container to Fly.io.
  4. The deploy job runs a smoke-probe (curl /health and /ready).
  5. Verify the deployed SHA matches the merged commit: curl -s https://quorum.stackclimb.com/status | jq -r .build_sha and compare to the merged commit SHA.

Do not trust /health 200 alone. A green health check only confirms the process is running, not that the latest code is deployed. Use the /status endpoint's build_sha field to verify the deployed version matches the expected commit. The deploy-drift watchdog runs on a schedule and alerts if main HEAD does not have a successful Deploy job.

Rollback: fly releases rollback. The rollback procedure is in DEPLOY.md. There is no automatic rollback on a failed smoke test — deliberate.

? What are the SLOs and how are they monitored?

SLOs (Service Level Objectives) are declared targets the operator holds the product to. The current SLOs:

  • Availability: 99% of requests answered non-5xx. Read from /metrics request-count status labels.
  • 5xx error rate: < 1% of requests. Same /metrics read.
  • Query latency: P50 ≤ 45s, P95 ≤ 120s, hard timeout 180s. Enforced by wall-clock deadline in the orchestration layer.
  • Non-run route latency: p95 < 1s. From /metrics request-duration histograms.
  • Readiness honesty: /ready reports live in production. Monitored by availability-check.yml (every 15 min).
  • E2E flake rate: 0 observed failures per full scan. Measured baseline: 0/960 (run 29911231157).

The ops dashboard at /ui/ops renders all current SLO values live from /metrics, /status, and /ready. It auto-refreshes every 10 seconds. Two alerting rules are mechanised: readiness-not-live (availability-check.yml, every 15 min) and error rate over SLO (error-rate-check.yml, every 30 min). Onboarding

Your step-by-step buddy: from "what is this?" to "I just shipped a feature."

? Step 0: What is the problem in plain words?

Right now, if you want a well-researched answer to a complex question, you open one AI chatbot, get one perspective, and hope it is good enough. If you ask four different chatbots the same question, you get four different answers — and no easy way to see where they agree, where they disagree, and which claims are backed by sources.

Quorum AI fixes that: one question, four models, one answer with the disagreement preserved. Cost is shown before anything runs. Nothing executes without your confirmation. Results are ephemeral (they disappear when you close the tab) — because a research tool is not a chat log.

The short version: "Ask four experts the same question, watch them debate, and get a synthesis that tells you what is settled, what is contested, and what you should do next."

● Built
? Step 1: The words explained

Before you touch the code, here are the words you will see everywhere, translated from jargon to plain English:

  • Repo = the project's file history on GitHub. URL: github.com/imrohitagrawal/quorum-ai.
  • Commit = a saved snapshot of the repo. Each has a short ID like 9555701.
  • Branch = an independent line of development. main is the production branch. Feature branches are named like feat/....
  • Pull request (PR) = a proposal to merge a branch into main. CI runs automatically; human review is required.
  • API = the set of URLs the app exposes for the browser to call. POST /v1/query-runs starts a run.
  • API key = a secret string that authenticates the app to an external service (like ). Stored server-side.
  • Model = a specific AI system, identified by vendor/version (e.g. openai/gpt-4o-mini).
  • Token = the billing unit for LLMs. ~4 chars of English text ≈ 1 token. Priced per 1,000 tokens.
  • FastAPI = the Python web framework. Like Flask, but with async support and automatic API docs.
  • Pydantic = a Python library for data validation. Config values and API request/response shapes are Pydantic models.
  • SQLite = a file-based database. No server process — just a file on disk. Quorum AI uses two: feedback_store.db and run_history_store.db.
  • Dockerfile = a recipe for building the app's container image. Contains the Python version, dependencies, and the command to start the server.
  • GitHub Actions = the CI/CD system. Every push runs tests automatically; merges to main trigger a deploy.
  • SLO = Service Level Objective — a target the product is measured against (e.g. "P95 latency under 120 seconds").
  • CSRF = Cross-Site Request Forgery. A token that proves the request came from the app's own page, not from a malicious site.

● Built
? Step 6: Follow one feature end to end

The best way to understand the codebase is to follow a single query from submission to result. Here is the path:

  1. Browser — user types a question in templates/workspace.html. JavaScript in static/app.js calls POST /v1/query-runs/estimate.
  2. Session — GET /v1/session issues a cookie + CSRF token. The CSRF token is sent as a header on every mutating request.
  3. Estimate — query_runs.py calls CostEstimationService.estimate() (in costs.py), which computes a realistic token-based cost and returns the three-band threshold action.
  4. Submit — browser calls POST /v1/query-runs with the query, four model slots, safety acknowledgements, and (if needed) the confirmation token.
  5. Orchestration — query_runs.py creates a QueryRun in accepted state and fans out to four provider calls via providers.py.
  6. Providers — each call hits with optional web search. Failures fall back to simulation. Results are stored as ModelAnswer objects.
  7. Debate — debate.py runs two critique rounds over the available answers.
  8. Synthesis — synthesis.py fans out five calls (one per section) and assembles the final output.
  9. Result — the browser polls GET /v1/query-runs/{id} for status updates, then renders the five synthesis sections plus the model answers, debate rounds, cost breakdown, and elapsed time.
  10. Evaluation — after the terminal transition, evaluation.py computes the deterministic RunEvaluation and TrustScore (Layer A). Optionally, the Layer B judge produces an advisory verdict.

At each step, the state machine in query_runs.py advances the run through draft → cost_review → accepted → initial_answers_running → debate_round_1_running → debate_round_2_running → synthesis_running → completed (or a terminal failure state).

Mentor

Practical senior advice from the trenches: treat AI as a fast junior, verify don't trust, plan first, measure before optimizing, watch cost, pin model versions.

? Treat AI as a fast junior, not an oracle

An LLM is knowledgeable, fast, and tireless — but it is also confident-wrong, forgetful, and will happily invent a plausible-sounding answer when it does not know. Treat it like a bright new hire who has read everything but has not yet developed judgment.

That means: check its work, verify its citations, question its assumptions, and never let it make a decision you would not also explain to your manager. Quorum AI's design acknowledges this: the debate step exists because one model confidently hallucinating is a failure mode; four models plus two critique rounds surface the disagreement that a single model would smooth over.

Mentor says

"The output of an LLM is a draft, not a fact. The synthesis step in Quorum AI is the first draft of your analysis — not the final answer. Read it critically, check the sources, and apply your own domain knowledge before acting on it."

In your project

The detect_refusal and citation_marker_grounding signals in the Layer-A evaluation module are designed to catch exactly this: a model that refuses to answer (a safety signal worth surfacing) and a model that cites sources it did not actually retrieve (a grounding failure). The TrustScore suppresses its numeric value while support_verified is False — because citation count alone does not prove a citation supports its claim.

Picture it in real life

A junior analyst writes a research memo. It is well-structured, confident, and thorough. But the manager does not publish it without checking the data sources, verifying the numbers, and asking "is this actually true?" The analyst is fast and knowledgeable, but the manager's judgment is the final gate. That is the right relationship with LLM output.

? Verify, don't trust

The single most important discipline in this codebase: if a number, status, or claim matters, measure it directly. Do not infer it from context, do not assume it from a previous state, do not accept it from a log line without checking the source.

Concrete applications:

  • Deploy verification: Do not trust /health 200. Check /status build_sha against the merged commit SHA. A green health check only confirms the old process is still running.
  • Test results: A green test on clean sim data is not proof the feature works on real LLM output. Render against the golden messy fixture and look at it as a user would.
  • Cost estimates: The guardrail keys off the fail-safe upper bound (max_cost_usd), not the point estimate. That bound prices every billable call's output at its enforced cap, including the Layer-B judge when one is configured (#265). Input sizes are modelled, not enforced, so treat it as the worst case the run is priced at rather than an absolute ceiling.
  • OpenAPI contract: Do not trust the hand-written spec. The drift guard byte-compares app.openapi() against the committed openapi.yaml. A mutated schema is caught.
  • Redaction: Do not trust "we strip secrets." The redaction tests assert it with static-analysis-style checks against real secret-shaped patterns.
Mentor says

"The cheapest command you can run is the one that proves your hypothesis. Before you say 'it works,' run the check that would catch it if it didn't. Before you say 'it's deployed,' check the build_sha. Before you say 'the estimate is accurate,' compare it to a measured actual. One check prevents a confidently-wrong conclusion."

? Measure before optimizing

Do not optimise a system you have not measured. The observability backbone (OD-1 through OD-7) exists so that every optimisation decision is grounded in data, not in a hunch.

The key metrics to watch:

  • P50 / P95 latency from /metrics request-duration histograms. Target: P50 ≤ 45s, P95 ≤ 120s.
  • 5xx rate from /metrics request-count status labels. Target: < 1%.
  • Provider call latency from per-request logs (each carries request_id and query_run_id for correlation).
  • Cost per run from the feedback store's cost_guardrail_accepted events.
  • Flake rate from the flake-scan workflow. Latest: 0/960.

The perf-sample CI workflow produces hermetic latency samples on every run. The advisory perf gate compares them to the declared targets. The numbers are advisory because the test environment does not represent production latency (no real network, no real LLM calls) — but trends are meaningful.

Mentor says

"If you cannot measure it, you cannot improve it. Before you spend a day refactoring for performance, check the current P95. If it is 80s and the target is 120s, your time is better spent on something else. If it is 110s, now you know what to optimise and you will know when you have succeeded."

● Built
? Watch cost like a hawk

Every LLM call costs money. The cost model in costs.py prices seven billed calls per query run (4 initial answers + 2 debate rounds + 5 synthesis sections). On the default model mix, a typical run costs between $0.01 and $0.03 — but a long query on expensive models can approach the $0.25 hard cap.

The guardrail is not optional. It is three-layered:

  1. Per-call estimate — the pre-run estimate prices every call and checks the three-band threshold before any provider is called.
  2. Cumulative spend — an in-memory ring buffer tracks accepted spend per account and blocks rapid-fire exhaust-the-budget attacks.
  3. Daily cap — the durable SQLite feedback store enforces a $0.20 per-account-per-24h rolling window, catching trickle attacks that the in-memory buffer misses.

The cost estimation is deliberately conservative: the point estimate models realistic token counts (grounded against a real live run that observed 2277–2560 prompt tokens and 465–1152 output tokens per model), and the guardrail keys off a fail-safe upper bound that prices initial-answer output at the enforced 2000-token cap. The estimate rarely falls below the measured actual.

Mentor says

"Cost is the one metric that compounds silently. A $0.02 leak per run, 100 runs a day, is $730/month. The cost guardrail is not a suggestion — it is a circuit breaker. And the estimate is deliberately conservative: it is better to over-estimate and confirm than to under-estimate and surprise. The guardrail keys off the upper bound for exactly this reason."

● Built
In your project

The costs.py module's _estimate_breakdown method prices each of the seven billed calls individually. The by_model partition shows four slot rows plus a "Debate + synthesis" row. The by_stage partition shows initial answers, debate round 1, debate round 2, and synthesis. Both re-sum to the quantized total exactly. The max_cost_usd field is always ≥ estimated_cost_usd and is what the guardrail checks — not the point estimate.

? Pin model versions, don't float

Model IDs in Quorum AI are pinned to specific versions: openai/gpt-4o-mini, not openai/gpt-4o. This matters because vendors silently update models, and an update can change the output quality, the token pricing, the safety behaviour, and the API contract — all without a deploy of your code.

The four default model IDs are the static source of truth in model_slots.py. The live catalog is a drift check, not the source. If the catalog has dropped a default model ID, the workspace shows a banner and the /v1/models/defaults endpoint surfaces stale_model_ids so an operator can react — without silently swapping to a different model mid-run.

The debate and synthesis models (DEBATE_MODEL_ID and SYNTHESIS_MODEL_ID in config.py) are also pinned. Their defaults are anthropic/claude-haiku-4.5 (debate) and openai/gpt-4o-mini (synthesis). The judge model (QUORUM_EVAL_JUDGE_MODEL_ID) is pinned because verdicts from different models are not comparable.

Mentor says

"Floating model IDs are a silent deployment risk. If you depend on gpt-4o and OpenAI releases gpt-4o-2025-06-13 with different behaviour, your tests still pass but your product changes. Pin the version. Monitor the drift. Decide when to upgrade deliberately."

In your project
